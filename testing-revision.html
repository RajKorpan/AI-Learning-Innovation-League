Test and Improve

Challenge the team’s assumptions with realistic evidence.

Testing is not a satisfaction survey. Teams compare what users say with what they actually do, look for changes in the target learning behavior, and assume the problem or solution may be wrong.

Five testing stages

1. Team self-test

Use test cases to identify obvious errors, answer substitution, confusing instructions, and inaccessible interactions.

2. Peer-team test

A different team tries the prototype without inside knowledge and identifies unclear assumptions.

3. Teacher-client review

The teacher checks whether the tool addresses the actual need, fits the context, and uses appropriate content.

4. Learner test

An appropriate learner uses the tool in a realistic context with permission and the option to stop.

5. Revised test

The team tests the changed behavior using comparable tasks and records what improved or remained unresolved.

Required observation record

  • What the user tried to do
  • Where the user hesitated
  • What the user misunderstood
  • What the user ignored
  • What the user used successfully
  • What the user said
  • What the user actually did
  • Whether the target learning behavior changed
  • What unexpected output or emotion appeared
  • What revision follows from the evidence
Assume you may be wrong: The purpose of testing is to challenge—not confirm—the team’s assumptions. A result may require redefining the problem or selecting a different strategy.

Responsible AI and accessibility checkpoint

Before leaving the testing stage

  • Do not enter identifying student data.
  • Obtain permission and allow users to stop.
  • Test in a realistic but safe context.
  • Observe harm, exclusion, frustration, dependence, and unexpected outputs.
  • Do not coach so much that the prototype appears more usable than it is.
  • Remove identifying details from evidence shared publicly.
