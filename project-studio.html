How to use the Studio

Each tool supports one project decision or record. Read the description and example before using the form. Work in order during a first cycle, but return to an earlier tool whenever interviews, research, or testing change your understanding.

  1. Analyze whether the problem is specific, observable, evidence-based, and feasible.Not started
  2. Break the task into knowledge, actions, prerequisites, decisions, and errors.Not started
  3. Record learning-science claims, sources, evidence strength, and design implications.Not started
  4. Place the selected component in a larger learning progression.Not started
  5. Generate an adaptive strategy sequence, feedback plan, fading plan, and test recommendation.Not started
  6. Compare non-AI, AI-assisted, conversational, and custom product paths.Not started
  7. Plan a low-resolution prototype, Gem, chatbot, or custom application.Not started
  8. Build structured AI instructions through a guided question-by-question wizard.Not started
  9. Record what users did and connect evidence to revision.Not started
Your work is not saved automatically. Download or copy each record before refreshing or leaving this page. Use “Download Project Packet” to combine the current outputs into one text file.
Privacy: Do not enter names, grades, medical information, account details, unapproved student work, or other identifying information into these tools.

1. Adaptive Problem Size Check

Not started

What it is

An adaptive check that considers the problem statement, target learner group, type of learning change, available evidence, timeline, access to testing, language, dependencies, and intended product scope.

Purpose

Determine whether the team has a specific, observable, evidence-based, and feasible learning problem—or which revision should happen before building.

How to use it

Choose the option that best matches the team’s current evidence. The tool weights essential criteria more heavily, identifies blockers and combinations, and generates a tailored problem frame and next steps.

Example: “Students struggle with graphs” is broad. A right-sized version is: “Students can identify the axes but cannot determine the interval represented between labeled points.”
What evidence supports the problem definition? Select all that apply.

Complete the fields to receive a readiness rating, blockers, strengths, and tailored next steps.

2. Task Analysis

Not started

What it is

A structured map of everything a successful learner must know and do to reach the final learning goal.

Purpose

Identify prerequisites, vocabulary, concepts, procedures, decisions, common errors, cognitive-load points, and the likely bottleneck.

How to use it

Complete the fields using teacher-client and learner evidence. Generate the map, review whether the selected bottleneck is truly necessary, and download it for the design notebook.

Example: For graph intervals, the learner must recognize labeled values, count spaces, divide the difference by the number of intervals, and check that the scale is consistent.

3. Learning-Science Evidence Record

Not started

What it is

A table for connecting a specific claim about learning to its source, evidence strength, learner need, and design implication.

Purpose

Keep the design grounded in verified learning science rather than AI suggestions, familiar myths, or unsupported claims.

How to use it

Enter one claim at a time. Cite the original source, rate the evidence, explain why it matters to this learner, and state what the team will design or test differently.

Example: Claim: “Retrieval practice can strengthen later recall.” Design implication: include short recall attempts before showing definitions, then test unaided recall.

4. Learning-Progression Map

Not started

What it is

A map showing what comes before the selected component, what competent performance looks like, and what the component enables later.

Purpose

Avoid treating a small skill in isolation and make sure the tool fits a larger disciplinary pathway.

How to use it

Describe prerequisites and commonly confused skills, then write observable beginning, developing, and proficient performance. Add what the component makes possible in later work.

Example: Beginning: recognizes axis labels. Developing: calculates intervals with prompts. Proficient: determines and explains an unlabeled interval independently.

5. Adaptive Strategy Matcher

Not started

What it is

A weighted comparison of learning strategies using the bottleneck, desired mental action, learner stage, error pattern, current support, evidence quality, feedback, timing, practice context, frequency, fading, and access constraints.

Purpose

Recommend a sequence of strategies and testing conditions rather than returning a generic list or treating the result as a diagnosis.

How to use it

Answer every field from interview, task-analysis, and performance evidence. The tool scores twelve strategies, explains the strongest matches, and generates feedback, fading, format, and testing recommendations.

Example: A novice who makes a systematic graph-scale error during guided practice may need contrasting cases and a worked example before error analysis and independent practice.
Which conditions should shape the recommended format? Select all that apply.

Complete the fields to compare strategy fit, confidence, feedback, fading, format, and testing recommendations.

6. Adaptive Product-Type Decision

Not started

What it is

A comparison of four product paths: non-AI, AI-assisted non-AI, conversational AI, and a custom application.

Purpose

Choose the simplest safe and testable product that fits the learner action, interaction, feedback, variability, data, platform, technical, timeline, access, and maintenance conditions.

How to use it

Answer every field and use “Yes,” “No,” or “Uncertain” for the decision gates. The tool scores all four paths, applies hard blockers, recommends a primary and backup path, and creates a prototype and safeguard plan.

Example: Adaptive dialogue may justify a Gem, but uncertain account rules or unverified feedback should move the team back to a paper conversation flow until those conditions are resolved.
Does AI provide a capability a simpler tool cannot provide as well?
Can generated content or feedback be verified?
Does the planned interaction preserve productive struggle and learner agency?
Can the product be tested safely and realistically?
Is an accessible low-tech alternative available?

Complete the fields to compare fit, blockers, safeguards, prototype formats, and testing recommendations.

7. Build Guidance

Not started

What it is

A planning guide for moving from a low-resolution prototype to a Gem, chatbot, or custom application when appropriate.

Purpose

Help the team build only what is needed to test the learning interaction and document safe, accessible versions.

How to use it

Begin with the simplest paper, storyboard, role-play, or mock transcript. Test the interaction, then add technology only when the evidence supports it. Record each version and the reason for the change.

Example: Role-play a question-decomposition coach with index cards before writing Gem instructions. Revise the hint sequence after a peer test.

Prototype before polishing

Use a paper conversation flow, storyboard, role-play, flashcard sample, prompt skeleton, mock transcript, one-question test, clickable wireframe, or small sample set. Build only enough to answer one question.

Build a Gem

  1. Use an existing Gem and identify its strengths and limitations.
  2. Modify one behavior and test the change.
  3. Name the new Gem for the learning action.
  4. Use the Prompt Builder to define the learner, need, component, bottleneck, evidence, productive struggle, feedback, reflection, fading, accessibility, and limits.
  5. Add example interactions for correct, partially correct, incorrect, repeated-error, irrelevant, and answer-request cases.
  6. Test edge cases, revise the instructions, and record a new version.
  7. Share only through advisor-approved settings.

Build a custom application

  • Build the smallest testable function first.
  • Separate the educational interaction from technical features.
  • Use approved data and services.
  • Plan human review and failure behavior.
  • Provide a low-tech fallback.
  • Document AI-generated code, content, and revisions.

Build checkpoint

  • Use age-appropriate and respectful language.
  • State tool limits.
  • Protect privacy and minimize data.
  • Preserve learner agency and productive struggle.
  • Include accessible formats and alternatives.
  • Test answer requests, hallucinations, bias, repeated errors, sensitive disclosures, and frustration.

8. Guided Learning-Design Prompt Builder

Not started

What it is

A seventeen-question wizard that builds reusable instructions for a conversational learning tool one decision at a time.

Purpose

Help students understand why every prompt component matters instead of confronting them with one long form.

How to use it

Read why each question matters, review how to respond and the example, enter one answer, and continue. Use earlier Project Studio work to prefill several questions, then review and edit before copying or downloading.

Example: A graph-scale coach asks the learner to explain the labeled values, waits for an attempt, gives one graduated hint, and asks the learner to check whether the interval is consistent.

9. Testing and Revision Log

Not started

What it is

A structured observation and revision record for team, peer, teacher-client, learner, and revised tests.

Purpose

Move beyond “Did you like it?” and capture what the user tried, hesitated over, ignored, used successfully, said, and actually did.

How to use it

State one question for the test, observe without over-coaching, enter the evidence, and write the revision that follows. After revising, use a comparable task and add a new record.

Example: A learner skipped the reflection prompt because it appeared after the final answer. The team moves it earlier and shortens it, then retests the same interaction pattern.
