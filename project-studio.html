How to use the Studio

Each tool supports one project decision or record. Read the description and example before using the form. Work in order during a first cycle, but return to an earlier tool whenever interviews, research, or testing change your understanding.

  1. Check whether the learning problem is specific and manageable.
  2. Break the task into knowledge, actions, prerequisites, decisions, and errors.
  3. Record learning-science claims, sources, evidence strength, and design implications.
  4. Place the selected component in a larger learning progression.
  5. Compare learning strategies that may fit the learner’s bottleneck.
  6. Decide whether the product should use AI and what type of tool to prototype.
  7. Plan a low-resolution prototype, Gem, chatbot, or custom application.
  8. Generate structured instructions when a conversational AI tool is appropriate.
  9. Record what users did and connect evidence to revision.
Privacy: Do not enter names, grades, medical information, account details, unapproved student work, or other identifying information into these tools.

1. Problem Size Check

What it is

A six-question check for deciding whether a broad learning challenge has been narrowed enough for a short team project.

Purpose

Prevent the team from trying to solve an entire subject or vague problem and confirm that improvement can be observed.

How to use it

Discuss each statement as a team and check it only when you have evidence. If fewer than six checks are met, return to interviews or task analysis and narrow the problem.

Example: Replace “students struggle with graphs” with “students can identify the axes but cannot determine the interval between labeled points.”

2. Task Analysis

What it is

A structured map of everything a successful learner must know and do to reach the final learning goal.

Purpose

Identify prerequisites, vocabulary, concepts, procedures, decisions, common errors, cognitive-load points, and the likely bottleneck.

How to use it

Complete the fields using teacher-client and learner evidence. Generate the map, review whether the selected bottleneck is truly necessary, and download it for the design notebook.

Example: For graph intervals, the learner must recognize labeled values, count spaces, divide the difference by the number of intervals, and check that the scale is consistent.

Generated task map

Complete the fields and generate a task map.

3. Learning-Science Evidence Record

What it is

A table for connecting a specific claim about learning to its source, evidence strength, learner need, and design implication.

Purpose

Keep the design grounded in verified learning science rather than AI suggestions, familiar myths, or unsupported claims.

How to use it

Enter one claim at a time. Cite the original source, rate the evidence, explain why it matters to this learner, and state what the team will design or test differently.

Example: Claim: “Retrieval practice can strengthen later recall.” Design implication: include short recall attempts before showing definitions, then test unaided recall.

4. Learning-Progression Map

What it is

A map showing what comes before the selected component, what competent performance looks like, and what the component enables later.

Purpose

Avoid treating a small skill in isolation and make sure the tool fits a larger disciplinary pathway.

How to use it

Describe prerequisites and commonly confused skills, then write observable beginning, developing, and proficient performance. Add what the component makes possible in later work.

Example: Beginning: recognizes axis labels. Developing: calculates intervals with prompts. Proficient: determines and explains an unlabeled interval independently.

5. Strategy Matcher

What it is

A guided comparison of learning strategies based on where the learner’s process breaks down, the mental action needed, feedback, and fading.

Purpose

Generate evidence-informed possibilities without treating the result as a diagnosis or automatic instructional decision.

How to use it

Select the challenge and mental action, then describe what the learner can already do and what evidence identifies the bottleneck. Compare the suggested strategies with the task analysis and research record.

Example: If a learner loses track of multi-step questions, the matcher may suggest task decomposition, worked examples with fading, and metacognitive monitoring.

6. Product-Type Decision

What it is

A decision check for comparing a non-AI tool, an AI-assisted non-AI tool, a conversational AI tool, or a custom application.

Purpose

Ensure that the team chooses technology because it adds educational value—not because it appears more advanced.

How to use it

Describe the problem and learner action, then check each condition only when the team can support it. Use the recommendation as a starting point and compare it with a paper prototype.

Example: If a static card sort can provide the needed comparison practice, conversational AI may not add enough value to justify its risks and complexity.

7. Build Guidance

What it is

A planning guide for moving from a low-resolution prototype to a Gem, chatbot, or custom application when appropriate.

Purpose

Help the team build only what is needed to test the learning interaction and document safe, accessible versions.

How to use it

Begin with the simplest paper, storyboard, role-play, or mock transcript. Test the interaction, then add technology only when the evidence supports it. Record each version and the reason for the change.

Example: Role-play a question-decomposition coach with index cards before writing Gem instructions. Revise the hint sequence after a peer test.

Prototype before polishing

Use a paper conversation flow, storyboard, role-play, flashcard sample, prompt skeleton, mock transcript, one-question test, clickable wireframe, or small sample set. Build only enough to answer one question.

Build a Gem

  1. Use an existing Gem and identify its strengths and limitations.
  2. Modify one behavior and test the change.
  3. Name the new Gem for the learning action.
  4. Use the Prompt Builder to define the learner, need, component, bottleneck, evidence, productive struggle, feedback, reflection, fading, accessibility, and limits.
  5. Add example interactions for correct, partially correct, incorrect, repeated-error, irrelevant, and answer-request cases.
  6. Test edge cases, revise the instructions, and record a new version.
  7. Share only through advisor-approved settings.

Build a custom application

  • Build the smallest testable function first.
  • Separate the educational interaction from technical features.
  • Use approved data and services.
  • Plan human review and failure behavior.
  • Provide a low-tech fallback.
  • Document AI-generated code, content, and revisions.

Build checkpoint

  • Use age-appropriate and respectful language.
  • State tool limits.
  • Protect privacy and minimize data.
  • Preserve learner agency and productive struggle.
  • Include accessible formats and alternatives.
  • Test answer requests, hallucinations, bias, repeated errors, sensitive disclosures, and frustration.

8. Learning-Design Prompt Builder

What it is

A generator for reusable instructions that define the learner, learning need, evidence, desired action, productive struggle, feedback, reflection, fading, accessibility, limits, and measurement.

Purpose

Create a conversational learning tool that asks before telling and supports thinking instead of acting as a conventional answer-giving tutor.

How to use it

Complete each field with information from interviews, task analysis, and research. Review the generated prompt, edit it with the team, test it in an approved platform, and document versions.

Example: A graph-scale coach asks the learner to explain the labeled values, gives one graduated hint, and asks the learner to check whether the interval is consistent rather than providing the answer.

9. Testing and Revision Log

What it is

A structured observation and revision record for team, peer, teacher-client, learner, and revised tests.

Purpose

Move beyond “Did you like it?” and capture what the user tried, hesitated over, ignored, used successfully, said, and actually did.

How to use it

State one question for the test, observe without over-coaching, enter the evidence, and write the revision that follows. After revising, use a comparable task and add a new record.

Example: A learner skipped the reflection prompt because it appeared after the final answer. The team moves it earlier and shortens it, then retests the same interaction pattern.
